# 1.5.4：页面加载优化与用户公告

状态：用户已批准实施，代码位于 `codex/v1.5.4-performance-announcements`。2026-09-16 编写，2026-09-17 收尾验收；原方案保留作为设计依据，实际完成情况与限制见第九节。

## 一、版本目标与边界

1. 定位“打开网页慢”发生在网络传输、脚本执行还是数据等待，缩短首次访问与再次访问的实际可用时间。
2. 管理员可发布公告，用户进入主页能发现消息；明确持续时间、确认后的展示、跨设备与内容更新规则。
3. 公告不得阻塞充电桩列表、刷新、提醒或扫码绑定；沿用现有浅深色、连续分区和键盘交互规范。

本版不建设营销系统，不发送公告微信推送，不增加用户分群、图片上传、富文本编辑器和强制阅读弹窗。保留现有充电桩快照与手动刷新业务边界，不通过高频请求远端换取“看起来更新快”。

## 二、加载速度：已知情况与尚待验证项

### 2.1 源码检查结果

| 观察 | 证据 | 结论与处理 |
| --- | --- | --- |
| 生产为 Next 静态导出，由 Go 提供资源 | `frontend/next.config.ts`、`backend/cmd/server/main.go` | 以生产构建测试，开发环境首次编译速度不能代表线上 |
| 已有 gzip、带 hash 文件一年 immutable 缓存，HTML 要求重新验证 | `backend/internal/api/middleware.go` | 不重复声称“缺少压缩/缓存”；核实线上反向代理和 CDN 实际响应 |
| 主页 HTML 直接引用 15 个 JS/CSS 文件 | 本地现存 `frontend/dist/dashboard/index.html` 及其引用文件 | 原始合计 1,036,236 字节，独立 gzip 估算 300,666 字节；HTML 22,259 字节。仅是现存本地产物采样，不是线上实测或全部运行时下载量 |
| 单份 CSS 原始 166,549 字节、gzip 估算 28,264 字节 | 同上 | 检查样式来源和原型页面贡献；不能未经分析直接删除共享样式 |
| 登录校验后并发请求快照、提醒、通知，但等待三者全部结束才清除主页初始化状态并连接 SSE | `frontend/components/workbench/dashboard-session.tsx` | 已确认存在等待耦合：慢的辅助请求延长初始化与部分按钮禁用；快照数据可能已显示，不能说整个列表必然一直空白 |
| 添加桩、使用说明静态导入；提醒规则弹窗已经动态导入 | `frontend/components/workbench/dashboard-workbench.tsx` | 对非首屏弹窗做依赖分析，再决定延迟加载；已有拆包保留 |
| 统计脚本使用 lazyOnload | `frontend/app/layout.tsx` | 通常不在首屏关键路径，暂无证据认定为主因；单独观察失败与耗时 |
| HTML 请求读取文件并计算 CSP hash；gzip 在请求时执行 | `backend/internal/api/static.go`、`middleware.go` | 仅列为 CPU 优化候选，先测量；不得以牺牲 CSP 或发布一致性换速度 |

### 2.2 还不能直接下的结论

已对部署域名进行页面访问和公开资源 HTTP 采样，见第八节。仍缺完整浏览器瀑布和服务器内部耗时，暂时不能确定 DNS/TLS、CDN 回源、跨区域网络、服务负载中谁占主导。不得仅凭包体积承诺线上提速百分比。

实施阶段分别记录：HTML 的 TTFB；JS/CSS 的传输字节与缓存命中；FCP、LCP、CLS、长任务；登录校验、快照、提醒、通知耗时；“主页主要操作可用”的自定义时间。持续 SSE 连接不作为 network idle 或加载完成的判断条件。

### 2.3 优化顺序

**P0：建立可比基线与解除初始化耦合。**

- 用同一生产构建流程，记录冷缓存首次进入、暖缓存重开、站内返回三组数据；覆盖登录页和用户主页，管理员页面做回归。
- 登录身份确定后，快照、提醒、通知分别管理加载与错误。主页主状态只等待快照；SSE 不再等待辅助请求。保留快照时间戳防倒退逻辑与断线恢复。
- 提醒/通知仍未加载时，相关区域显示局部加载或重试，不显示为零、不允许基于未知状态重复创建提醒。辅助接口失败不阻塞桩列表；身份校验失败仍按原登录流程处理。
- 在网络限速与辅助接口故意延迟/失败时验证主操作可用，避免只测正常快网。

**P1：减小首屏下载与执行量。**

- 根据构建依赖和浏览器覆盖率拆分添加桩、说明等非首屏内容，复用已有动态组件方式。弹窗首次打开有局部加载、失败重试，点击不丢失；键盘焦点与表单草稿不受影响。
- 排查重复依赖、非必要路由预取、原型专用资源是否混入正式页；按证据删除或隔离，不进行无收益的组件库替换。
- 对常用交互可在 hover/focus 后预载，避免用户首次点击体验退化；不在首屏一次性预载所有弹窗抵消拆包收益。

**P2：按线上实测处理传输和服务端。**

- 核实源站与代理/CDN 的 Content-Encoding、Cache-Control、Vary、状态码和资源是否带 hash；暖缓存不得重复完整传输同版本静态资源。
- API 继续禁止共享缓存；HTML 继续重新验证。检查部署期间旧页面引用资源的可用性，必要时保留上一版 hash 资源，不能通过给 HTML 长缓存规避请求。
- 只有确认 gzip CPU 开销明显时，才增加构建预压缩产物/对应协商逻辑，保留原文件回退、正确 MIME、条件请求和 HEAD；禁止压缩/缓冲 SSE。
- 只有确认 CSP 计算显著时才考虑缓存，缓存必须绑定实际 HTML 内容/构建版本并在发布时失效。此项不是本版必做。

### 2.4 性能验收建议

- 固定浏览器版本、生产模式、同一数据量和 4 倍 CPU 降速；网络设为下行 1.6 Mbps、上行 750 Kbps、延迟 150 ms。冷/暖缓存各至少 5 次，记录中位数与最慢值，不能挑最佳截图。
- 在相同受控环境，目标是主页主要操作可用时间比基线缩短至少 20%；若基线已快或网络主导，记录结果和原因，不为达标造假。
- 非关键请求延迟 10 秒或失败时，快照成功后主列表与正常刷新不得继续等待这 10 秒。
- 首屏 JS/CSS gzip 预算以重新构建后的基线为准，目标减少至少 15%；如果依赖分析无法安全达到，记录实际收益与取舍。公告摘要相关新增 JS gzip 预算不超过 10 KB，详情/编辑器按需加载。
- 标准受控场景目标 LCP ≤ 2.5 秒、CLS ≤ 0.1；这是验收目标，不是当前线上数据。公告加载不得明显挤动正在操作的页面。
- 不新增控制台错误、重复登录检查/重复全量快照请求；脱机、弱网、冷缓存与发布后首次重开均可恢复。

## 三、公告产品方案（推荐规则）

### 3.1 入口与展示

- 用户主页标题/操作区下方、充电桩列表上方，放一条横向公告摘要，展示“公告/重要公告”、标题、时间、未确认数量及“查看”。不用全屏弹窗，不自动打开详情。
- 只展开当前优先级最高的一条，其余通过“全部公告”查看，避免多条公告撑满移动端。重要优先，同级按实际开始时间倒序，最后用 ID 稳定排序。
- 有效普通公告未确认时显示摘要；确认后从主动摘要中收起。重要公告在有效期内一直保留摘要，确认后去掉未确认标记，并显示“已确认”。
- “全部公告”作为标题区域固定的小入口，包含有效公告和已过期公告（分页）；过期记录标识“已结束”，已撤下公告不再向用户提供。
- 桌面打开侧边详情、移动端使用适配的小屏详情面板，复用现有 Dialog/Sheet。支持 Esc、关闭后焦点返回、分享站内公告深链接、浏览器返回关闭详情且保留桩筛选/选择。
- 详情底部使用“我知道了”明确记录确认；仅进入主页、展示摘要或打开详情不自动记录确认，关闭详情也不等于确认。不将确认人数称为实际阅读人数。

### 3.2 用户再次进入时的规则

| 情况 | 普通公告 | 重要公告 |
| --- | --- | --- |
| 已发布且在有效期内，尚未确认 | 显示主页摘要和未确认标记 | 显示主页摘要和未确认标记 |
| 看了详情但没点“我知道了” | 下次仍主动展示 | 下次仍主动展示 |
| 点击“我知道了”成功 | 主动摘要收起；全部公告仍可看 | 摘要继续显示为已确认，直到结束 |
| 刷新网页、退出后登录、换设备 | 同一账号沿用服务端确认状态 | 同左 |
| 管理员保存文字修正、不重新提醒 | 保留原确认状态 | 保留原确认状态 |
| 管理员选择“更新并重新提醒” | 作为新提醒版本再次显示 | 再次显示未确认标记 |
| 到期 | 主动摘要消失，全部公告内只读 | 同左 |
| 管理员提前撤下 | 摘要、列表及详情均不再显示 | 同左 |
| 新注册/从未登录的用户进入 | 显示仍有效的公告 | 同左 |
| 离线时点击确认 | 不假装确认成功，提示联网后重试 | 同左 |

不提供“每天弹一次”或“每次登录弹一次”，避免反复打扰。管理员如果只是延长结束时间，不重置确认状态；改变提醒级别或实质内容时，应明确选择是否重新提醒。

### 3.3 公告持续时间

- 状态：草稿 → 定时待发布/展示中 → 已结束；任意已发布公告可提前撤下。草稿可删除，已发布记录不物理删除，用于审计。
- 默认立即开始、7 天后结束；可自定开始和结束时间。允许“长期有效”，必须由管理员显式勾选，不默认永久保留。
- 生效边界：`startAt <= 服务端当前时间 < endAt`；长期有效无 endAt。结束必须晚于开始，不允许新发布已经结束的公告。
- 管理端清晰标注北京时间（Asia/Shanghai）；API/数据库使用 UTC 时间，避免服务器时区导致偏差。
- 不依赖独立定时任务改变数据库状态：读取时按服务端时间计算是否生效，定时发布不会因调度漏跑而失效。
- 已结束/撤下的公告不直接恢复为原版本，以“复制为草稿”重新发布，防止旧确认状态导致新消息无人看到。

### 3.4 页面打开期间如何更新

- 完成身份校验后独立加载公告摘要，不并入主数据初始化等待链。固定公告入口先可操作；短小预留区域避免请求完成后把桩列表向下挤动，无公告时呈现低调的“暂无公告”。
- 页面首次进入、站内回到主页及恢复可见时检查；去重并节流为至少间隔 60 秒。页面持续可见时每 5 分钟检查一次，隐藏或离线暂停；本版不新增 SSE 公告事件。
- 用户当前正在操作时不自动打开详情、抢焦点或扩张公告区域，只更新摘要。
- 响应包含 serverNow 与最近生效/到期边界，在可见页面到达边界时重新获取；断网不靠本机时间宣称公告已更新。
- 已打开详情被修改时不静默替换正文：显示“公告已更新，请重新查看”；旧提醒版本不能确认新版本。被撤下则显示“该公告已撤下”，提供返回。
- 公告请求失败只影响公告区域：显示“公告暂时无法加载 / 重试”；有本次会话数据则标明“离线，公告可能已更新”。不跨账号复用，不持久化个人状态到公共缓存。

## 四、管理员操作闭环

在现有管理员导航增加“公告管理”，使用对象列表加详情编辑区，不新增统计卡墙。

1. 列表按草稿、待发布、展示中、已结束、已撤下筛选；支持标题搜索、分页、打开详情与返回。
2. 新建填写标题（1–60 字）、正文（1–4000 字）、普通/重要、开始及结束时间。1.5.4 使用纯文本并保留换行；可选一个链接按钮（文案 1–20 字、地址不超过 2048 字符）。地址仅允许合法站内相对路径或 HTTPS，拒绝脚本协议和协议相对 URL。
3. 保存草稿、预览用户效果、发布。预览包含“有效期内会怎样显示、确认后是否保留摘要”，帮助管理员选择级别。
4. 编辑已发布内容时默认保存修正并保留确认状态；“更新并重新提醒”是独立动作，提交前展示其会重新提醒所有普通用户的效果。两者都产生内容修订记录。
5. 发布/更新/撤下防重复提交、失败保留草稿；多个管理员同时编辑以版本号校验，冲突时提示重新加载，不覆盖他人改动。
6. 撤下需确认，因为会立即撤销用户访问；记录操作者、时间、公告 ID 与动作。正文修订保存在版本表，不塞入冗长操作日志。
7. 首版不做曝光率、阅读率或用户阅读排行榜；若保留确认总数，只标为“主动确认人数”，不以其证明用户确实读懂。

## 五、数据与接口草案

具体命名在实施时跟随现有后端约定；下面明确必须满足的语义。

### 5.1 持久化

- `announcements`：ID、当前内容修订号、提醒版本号、标题、正文、可选链接、级别、发布/撤下标记、开始/结束时间、创建/修改人及时间、乐观锁版本。
- `announcement_revisions`：不可变内容修订和相关操作元数据；用于管理员回看，不向普通用户暴露内部信息。
- `announcement_acknowledgements`：userId、announcementId、reminderVersion、acknowledgedAt，联合唯一键，重复确认幂等。
- 内容修订与提醒版本分开：文字修正只递增前者，重新提醒同时递增后者。发布和确认在事务中校验有效期及版本。
- 默认面向所有普通用户，包括公告有效期内新注册的用户；管理员通过预览查看，首版不增加角色/账号定向功能。
- 新表采用增量迁移及索引，空数据库/已有数据库均可升级；不删除已有业务数据。已结束记录保留用于回看，暂不自动清理。

### 5.2 拟新增接口

| 接口 | 职责 |
| --- | --- |
| `GET /api/announcements/summary` | 返回主动摘要候选、有效未确认数量、serverNow、下一时间边界；正文不随摘要全量返回 |
| `GET /api/announcements` | 当前用户可见公告分页列表（有效/已结束），包含确认状态 |
| `GET /api/announcements/{id}` | 校验可见性后的完整详情、内容修订与提醒版本 |
| `POST /api/announcements/{id}/acknowledge` | 提交已查看的修订及提醒版本；校验并幂等记录当前账号确认 |
| `GET/POST /api/admin/announcements` | 管理员查询及创建草稿 |
| `GET/PATCH /api/admin/announcements/{id}` | 管理员详情及带版本条件的编辑 |
| `POST /api/admin/announcements/{id}/publish` | 发布，明确时间与提醒策略 |
| `POST /api/admin/announcements/{id}/withdraw` | 提前撤下 |
| `DELETE /api/admin/announcements/{id}` | 仅删除未发布草稿 |

用户接口要求登录且仅普通用户可用，管理接口要求管理员；不能接收客户端传来的 userId 作为确认身份。所有个性化响应保持 private/no-store，不通过 CDN 共享。过期可读不可新增确认、撤下不可读，草稿不可被猜 ID 读取。新版本确认冲突返回可恢复的 409；失效/不存在按现有错误风格统一处理。

## 六、实施与验收顺序（评审通过后）

1. 从最新主分支开 `codex/v1.5.4-performance-announcements`，保存生产性能基线与线上证据；不直接在 main 开发。
2. 先完成初始化解耦与有依据的资源优化，独立验证收益，再加入公告，避免无法区分性能变化来源。
3. 完成公告表迁移、生命周期、权限及确认状态接口；再完成管理端发布闭环与用户展示/详情/确认闭环。
4. 更新 1.5.4 版本来源、OpenAPI 和生成类型、部署说明及验收记录，保持前后端版本一致。
5. 单元/API 测试覆盖时间边界（含刚好结束）、定时生效、跨账号隔离、重复确认、内容修正不重提醒、重新提醒、过期/撤下、旧版本确认、管理员并发编辑及迁移。
6. 浏览器实测首次/再次进入、刷新、跨标签页/跨设备会话、深链接、返回、键盘确认、320/390/768/1440px、浅深色及减少动态效果。跨设备用同账号独立浏览器上下文验证服务端状态，不靠同一 localStorage。
7. 注入快照/提醒/通知/公告分别慢响应、失败及离线；确认公告始终不阻塞充电桩业务，网络恢复后可重试，已读状态不会串账号。
8. 执行全量检查、构建、Go 竞态检测和浏览器回归；按同一口径记录优化前、优化后及加入公告后的指标。
9. 输出代码审查与验收结果。先备份数据库再部署；回滚前验证旧程序对新 schema 的兼容性，不能承诺只替换二进制就一定能回退。不自动推送或部署。

## 七、本次需要评审的产品选择

### 8.4 据此调整性能实施优先级

1. **保留已生效的 gzip 与 immutable 缓存，暂不把预压缩/CSP 缓存作为首要任务。** 当前证据优先指向请求等待和连接路径，而不是缺少基础缓存。
2. **先测浏览器请求链，再完成主页初始化解耦。** 分别量化入口跳转、身份校验、快照和两个辅助请求；仍保留第二节已经确认的等待耦合修复计划。
3. **把连接复用与访问路径纳入基线。** 实施时在真实浏览器比较首次导航、同一连接后续资源、普通刷新和站内返回；curl 新连接的秒级耗时不能乘以资源个数估算整页耗时。
4. **线上与本地受控环境分开验收。** 受控限速测试用于比较代码收益；部署站点从用户实际常用网络补测至少 5 次冷/暖样本，记录地区、网络、代理情况、节点、时间与版本。LAX 单路径不用于承诺国内用户提速。
5. 如果实际常用网络仍以文档/连接等待为主，再评估代理/CDN 路径、回源与域名接入；如果主要为 JavaScript 执行，则先拆包。如果 API 主导，再依据具体接口耗时处理后端。保留 API 不共享缓存与 SSE 不缓冲的约束。

### 8.5 据此细化公告落位与请求预算

- 本站主页现有标题、刷新/添加操作、异常提示、搜索筛选均保留。公告放在标题操作区之后、业务列表之前；凭据异常使用独立明确区域，并在视觉优先级上高于普通公告。

- 摘要响应默认最多 3 KB 未压缩 JSON（不含 HTTP 头），只返回最高优先摘要、数量和时间边界，不返回全部公告正文或逐用户确认列表。公告路由不可提前全量预取详情。

## 十、公告提交故障复审（2026-09-17）
