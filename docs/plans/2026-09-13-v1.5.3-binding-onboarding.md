# 1.5.3 设计计划：添加充电桩前的绑定引导与扫码确认

状态：用户已批准，功能已实现；自动化结果与真实扫码待验项见 [验收记录](2026-09-13-v1.5.3-binding-acceptance.md)。
日期：2026-09-13。

## 1. 版本目标

让第一次使用的用户在添加充电桩时完成必要的微信绑定，不必先阅读说明或寻找账户设置；让用户明确知道：手机微信授权完成后，还需要在本站点击“确认绑定”。

本次为 1.5.3 计划内容。评审阶段只新增本文件，不改功能、不升级版本号、不部署、不提交或合并分支，也不改动已有的凭据恢复修复。实施前重新确认分支，并在独立的 1.5.3 开发分支工作。

## 2. 现状与具体问题

已核对 `add-pile-dialog.tsx`、`yyb-login-dialog.tsx`、后端设备及凭据接口，以及本机 yyb_go 的扫码状态实现。

1. 添加弹窗只在说明中提示先扫码；提交失败主要通过 toast 显示，没有就地前往绑定的操作。
2. 后端存在 `YYB_BINDING_REQUIRED` 错误码，但添加界面没有把它变为可继续操作的引导。
3. 绑定弹窗的确认按钮目前仅判断“存在二维码、没有正在确认”，未等待授权成功。
4. 当前文案“系统会自动确认扫码结果并保存”与实际需要点击确认的行为矛盾。
5. 自动轮询连续失败后会停止，但缺少醒目的停止检测提示；二维码与旧请求的生命周期也需要梳理。
6. 绑定状态接口只提供 `bound` 等信息，没有标明当前部署是否启用扫码能力。不能把未绑定一律当作必须扫码，误伤手动 Cookie 部署。
7. 已有确认接口先保存绑定，再尝试为已有设备同步凭据。`bound=true` 和 `cookieSynced=true` 是两个不同结果，首次没有设备时，未同步不代表绑定失败。

## 3. 推荐交互决策

- 点击“添加充电桩”后先检查绑定状态；启用扫码且未绑定时，自动进入绑定步骤。
- 使用一个弹窗容器，在“绑定微信 → 填写充电桩”两个步骤之间切换，不叠加第二个弹窗。
- 进入绑定步骤后自动生成一次二维码，失败后由用户点“重新生成”，不循环自动生成。
- 微信授权成功后，“确认绑定”从禁用变为可点，配合持续显示的状态提示，不只弹 toast。
- 用户点击确认，本站保存成功后，先展示“绑定成功”，提供“继续添加充电桩”。不立刻消失，让用户看清结果。
- 返回添加表单后保留之前输入；由用户明确点击“添加”，不自动重放添加请求。
- 仅在用户发起添加或绑定操作时引导，不在每次登录、打开首页时强制弹出。

以上交互已获用户确认，按此实施。

## 4. 添加入口流程

### 4.1 初次进入

所有正式添加入口共用同一控制逻辑，包括页面顶部、空列表中的添加按钮。

| 检查结果 | 展示和行为 |
| --- | --- |
| 正在检查 | 在添加弹窗中显示“正在检查平台连接…”，阻止重复提交 |
| 扫码能力已启用，未绑定 | 显示绑定步骤，标题“添加前，先绑定微信”，自动生成一次二维码 |
| 已绑定，没有明确要求重新扫码 | 进入添加表单；不因为用户很久没用就强制重绑，也不在打开时主动同步凭据 |
| 已绑定，服务明确要求重新扫码 | 显示“平台登录需要重新确认”，进入重新扫码流程，不先删除旧绑定 |
| 未配置扫码能力 | 保留原有手动凭据路径，显示手动设置入口；不弹无法完成的扫码流程 |
| 查询失败或当前离线 | 显示“暂时无法检查平台连接”与重试/关闭；不能把失败当成未绑定 |

绑定检查不得消耗远端充电桩刷新额度。已有绑定也不承诺永久有效，最终添加结果仍由后端判断。

### 4.2 添加失败后的恢复

| 失败类型 | 就地反馈 |
| --- | --- |
| `YYB_BINDING_REQUIRED` | 表单内显示“添加前需要先绑定微信”，操作“去绑定”；点击进入同一弹窗的绑定步骤 |
| `YYB_RESCAN_REQUIRED` 或等价明确状态 | 显示“平台登录需要重新确认”，操作“重新扫码” |
| 桩号格式错误、设备不存在、数量限制 | 保持输入，显示相应错误，不引导绑定 |
| 网络异常、扫码服务暂不可用 | 保持输入，允许重试，不将其描述为账号过期 |
| 本站登录失效 | 使用现有本站登录失效流程，不能误导为微信绑定问题 |

打开时的检查与提交时的后端验证都要保留：多标签页解除绑定或状态变化仍可能发生。

### 4.3 输入与返回

- 桩号、名称、位置及高级字段由添加流程父级保存，切换绑定步骤不清空。
- 绑定成功点击“继续添加充电桩”，返回原表单并聚焦桩号或下一待填字段。
- 尚未完成绑定时可关闭流程；若已经填写表单，提供“返回填写”恢复草稿，但未满足前置条件不能提交。
- 关闭弹窗后保留本次页面会话中的草稿，刷新页面不承诺恢复；不将凭据或二维码持久化到浏览器存储。
- 添加成功才清空草稿，进入已有“新增桩定位”逻辑。

## 5. 扫码步骤与按钮状态

主操作按钮位置和宽度稳定；所有状态下保留“确认绑定”位置，不让文字变化挤动布局。只有当前二维码会话收到明确可确认的业务状态，且在线、未提交时，按钮可用。HTTP 200 本身不代表扫码授权成功。

| 状态 | 页面主要提示 | 确认按钮 | 辅助操作 |
| --- | --- | --- | --- |
| 正在生成 | 正在生成二维码… | 禁用 | 关闭 |
| 等待扫码 `pending` | 请用微信扫一扫 | 禁用 | 重新生成、检查状态 |
| 已扫描 `scanned` | 已扫码，请在微信中确认授权 | 禁用 | 检查状态 |
| 已授权 `authorized` | 微信已授权，请点击下方“确认绑定”完成绑定 | 启用、品牌色 | 必要时重新生成 |
| 上游已确认 `confirmed` | 微信授权已完成，请点击“确认绑定”保存到当前账户 | 启用 | 同上 |
| 正在提交 | 正在确认绑定… | 禁用并显示加载状态 | 阻止重复提交；处理关闭意图，避免返回后自动添加 |
| 本站保存成功 `bound=true` | 绑定成功，可以继续添加充电桩 | 替换为“继续添加充电桩”或“完成” | 由入口决定 |
| 过期、取消、未知会话 | 二维码已失效，请重新生成 | 禁用 | 重新生成 |
| 连续检测失败/离线 | 暂时无法确认扫码结果，请恢复连接后重新检查 | 禁用 | 重新检查、关闭 |
| 确认请求失败 | 绑定未确认完成，请重试 | 先核对服务端状态后决定是否重新启用 | 重新检查、重新生成 |

`confirmed` 是扫码服务的会话状态，不可直接等同于本站绑定已保存。对支持的服务端版本进行契约测试；未知状态一律不放行。

### 文案层级

二维码附近为步骤说明，状态区在按钮上方，按钮下方补充一句：

> 微信授权后，还需点击“确认绑定”，才能保存到当前账户。

收到授权时：

> 微信已授权，最后一步：点击“确认绑定”。

绑定成功但没有设备时：

> 微信已绑定，接下来添加你的常用充电桩。

已有设备、绑定已保存但凭据同步失败时：

> 微信已绑定，但平台连接暂未恢复。可稍后重试同步。

此时保留绑定结果，不退回“未绑定”，不以绿色“全部完成”掩盖同步失败。账户入口提供同步操作；添加入口允许返回填写，由添加接口执行必要校验。

移除“自动保存绑定”和“以后会一直保持登录有效”等不准确承诺。手机扫码方式限制以实际扫码能力为准，沿用已验证的操作指引，不增加未经验证的相册识别入口。

## 6. 会话、轮询与重复请求

1. 保留约 3 秒检测间隔，使用串行调度；上一次未结束不发起下一次，手动检查也不得并发。
2. 关闭、换码、完成绑定或终态时，取消请求或使返回失效；通过会话 ID 与请求版本判断，旧二维码响应不能点亮新二维码的按钮。
3. 使用独立的二维码会话状态判断是否轮询；不能因为存在旧 `binding.bound=true` 就停止重新绑定的扫码检测。
4. 收到可确认状态后停止周期轮询，进入待用户确认阶段；提交时仍由后端验证二维码有效性。
5. 连续 3 次检测失败后停止自动检测，显示明确反馈；用户手动重试成功后按当前状态恢复流程。
6. 重新生成时立即清除旧授权状态并禁用确认；失败也不能回退为旧码可确认。
7. 确认期间防双击；若响应超时，先查询绑定状态，而非直接再次确认或添加。重新绑定场景不能仅用旧 `bound=true` 推断新会话成功，需要确认结果或服务器会话关联证据。
8. 本站已有“绑定保存成功、随后同步失败”的分阶段逻辑，实施时保证返回结果能表达绑定是否已经提交。保存已成功的异常路径不能返回含糊的“绑定失败”。
9. 后端始终校验会话归属及授权状态。按钮禁用只是用户引导，不能替代服务端验证。

## 7. 接口计划与兼容策略

优先复用：

- `GET /api/session/yyb-binding`
- `POST /api/session/yyb-qr`
- `GET /api/session/yyb-qr/{sessionId}/poll`
- `POST /api/session/yyb-qr/{sessionId}/confirm`
- `POST /api/piles`

计划为绑定状态响应新增可选 `scanEnabled`，由后端根据实际集成配置决定，不能从 `bound=false` 推断。它表示功能已配置，不表示扫码服务此刻健康。旧响应缺少字段时，不强制拦截原有添加流程，依赖提交错误引导并提供设置入口。

统一将“未绑定”“明确需要重新扫码”映射到稳定错误码；其他失败不附会为绑定问题。确认接口需区分绑定保存结果与凭据同步结果。若现有响应无法可靠确认新会话是否已提交，增加会话级确认状态/幂等结果，不通过泄露 OpenID、Cookie、ref 或 code 来关联。

实施前以真实 sidecar 契约验证这些状态，不仅依赖 mock。兼容分支纳入 OpenAPI 1.5.3 与契约测试。

## 8. 组件与视觉方案

- 复用 shadcn/ui / Base UI 的 Dialog、Button、Alert 与表单组件；抽出不自带弹窗的扫码步骤内容，供添加流程与账户设置共用。
- 添加弹窗管理草稿与步骤；扫码内容管理扫码会话，并通过 `onBound` / 返回事件通知上层，不直接提交充电桩。
- 标题下使用紧凑的两步文字进度“绑定微信 / 添加充电桩”；账户独立绑定不显示无关的添加步骤。
- 中性背景、品牌色主操作；等待、可确认、失败通过图标和文字共同区分，不只依赖颜色。
- 二维码、提示区、操作区连续分区；不使用卡片套卡片、全屏庆祝或闪烁动画。
- 轻量状态过渡不移动主要按钮，不自动抢焦点；减少动态效果时关闭非必要过渡。
- 手机界面保证按钮和关键状态易发现；二维码不被过度压缩，内容可滚动。
- 状态提示使用 `aria-live="polite"`，严重错误使用 alert；键盘可完成重试、确认、返回和关闭，焦点恢复到合理入口。

## 11. 本版边界与已确认决策

范围仅为添加前绑定引导与扫码完成确认体验。凭据长期恢复失败的根因排查属于已有修复工作，不在本计划中宣称解决；不新增后台保活、不改变刷新额度、不恢复使用历史。

用户已确认以下三个选择：

1. 未绑定时直接显示绑定步骤，并自动生成一次二维码。
2. 绑定成功后显示“继续添加充电桩”，由用户点击返回，不立即自动跳走。
3. 保留已填信息，回到表单后由用户重新点击“添加”，不自动提交。
